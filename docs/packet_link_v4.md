# V4：CRC16 数据包与双软件节点闭环

这个独立于历史 BER 实验的模块，把文本编码、成帧、BFSK 发射、盲接收、CRC 校验、应用层交付和声学波形 ACK 串成一个可运行的软件链路。接收节点的成功判断来自收到的帧字段和 CRC，发送端真值只在测试程序中用于验证输出。测试环境是延时、整体多普勒和 AWGN 的合成信道；没有将本模块描述成实测信道验证或单片机 Modem。

## 运行

在仓库根目录启动 MATLAB R2020b（需要 Signal Processing Toolbox）：

```matlab
addpath('matlab');
validate_packet_link_v4;
run_packet_link_v4;
```

结果保存在 `results/v4/packet_link/`。`validation.json` 与 `demo.json` 的 `status` 必须为 `PASS`；逐项检查和丢包事件分别在 `validation_cases.csv`、`demo_scenarios.csv`、`demo_events.csv`。演示输出节点 B 解码得到的 `你好，水声 Modem!`，JSON 同时保存接收文本。

已保存的本轮结果为 **35/35 项检查通过**；逐一翻转 DATA 帧的 256 个 bit，256 次均被拒绝。五种演示全部通过：

|场景|A 发送次数|A 状态|B 应用交付次数|
|---|---:|---|---:|
|正常|1|收到 ACK，完成|1|
|首次 DATA 丢失|2|收到 ACK，完成|1|
|首次 ACK 丢失|2|收到 ACK，完成|1|
|全部 DATA 丢失|3|交付未确认|0|
|全部 ACK 丢失|3|交付未确认|1|

`provenance.json` 固定本轮源码依赖和输出文件的 SHA256，供仓库独立核验。开发时首次空消息检查因测试比较 0×0 与 1×0 空数组而失败；接收结果当时已为 `crc_valid`。该次测试证据与修正说明保存在 `development_checks/`，当前表格使用完整复跑结果。

## 空中帧格式

物理层保持公开的 HFM UP/DOWN、两个已知单音导频和非相干 BFSK。BFSK 区域发送以下字节；字节内高位先发，多字节整数使用网络序（高字节在先）。这些协议字段是本项目新增设计，不是原论文的完整协议复刻。

|字段|字节数|内容|
|---|---:|---|
|Magic|2|`D3 91`，成帧标识；HFM 承担波形捕获|
|Version|1|`01`|
|Type|1|`01`=DATA，`02`=ACK|
|Sequence|2|0–65535，成功后模 65536 递增|
|Length|2|载荷字节数；当前上限 64；ACK 必须为 0|
|Payload|Length|DATA 为 UTF-8 编码字节；允许空消息|
|CRC16|2|覆盖前面全部头部与载荷，高字节在先|

CRC 使用 **CRC-16/CCITT-FALSE**：多项式 `0x1021`，初值 `0xFFFF`，输入/输出不反射，最终异或 `0x0000`。标准检查输入 ASCII `123456789` 得到 `0x29B1`。CRC 用于检测传输错误，不提供身份认证，也不保证任意多比特错误都能检出。

默认 48 kHz，两个 BFSK 频率 13,875/14,125 Hz，每比特发声 8 ms、无额外保护时间；HFM 和导频相对时序沿用 `uac2.default_config`。64 字节最大载荷对应 592 个 BFSK bit，总发射时间 5.264 s；空载荷 ACK 为 80 bit，总时间 1.168 s。这是透明、便于验证的最小协议，头部开销未做低功耗优化。

## 接收端如何摆脱真值

`uaclink.receive(waveform,cfg)` 只接收波形和双方预先约定的公开配置。

1. 由 `uac4.receive_timing` 的固定主峰规则捕获 HFM、估计时间尺度，并先解调固定的 64 bit 头部。
2. 检查 Magic、Version、Type、长度上限和 ACK 零载荷约束。无效长度在完整载荷解调和相关内存分配前被拒绝。
3. 使用头部 Length 推出帧长。沿用第一次捕获的起点与时间尺度，由 `uac4.decode_fractional` 解调整个帧，不重新选择同步位置。
4. 对实际解调字节检查长度与 CRC；只有 `valid=true` 才将载荷交给节点状态机。截断、CRC 不符、静音或未捕获都不交付消息。

接收函数没有发送比特、真实载荷长度、起始样点、速度或信道响应参数。协议解析后的长度与测试程序保存的发送长度是不同来源。

当前接口处理一个接收窗口中的一帧；窗口内只寻找最强候选，不实现持续音频流中的多帧搜索、逐帧消费或随机接入。接收窗口由仿真事件调度器提供，窗口内的到达位置未知。

## 两节点与 ACK / 超时

`uaclink.new_node` 创建独立状态。`send_message` 将 UTF-8 文本封装为 DATA 并进入 `waiting_ack`；`on_waveform` 通过完整接收函数处理 DATA 或 ACK；`on_timeout` 依据本地时间重发。

- B 首次收到期待的序号且 CRC 有效时，交付一次载荷，并将 ACK 也封装、CRC 编码、BFSK 调制。A 必须从收到的 ACK 波形解码，才能清除等待状态。
- B 收到相同序号且载荷相同的重发 DATA 时，只重发 ACK，避免应用重复交付。同序号不同载荷、未来序号和不匹配的 ACK 均不推进状态。
- 默认一次原始发送加最多两次重发；等待时限为 DATA 发射结束后 2 s。在本合成信道里，这覆盖 ACK 发射及模拟延时。测试确认正常 ACK 在时限内到达。
- 三次发送仍未收到匹配 ACK，则 A 进入 `exhausted`，含义为**交付未获确认**。如果只是全部 ACK 丢失，B 可能早已成功交付；程序保留这一事实，不声称接收端一定没有收到。

这是预先配对、单会话的点对点模型，不带地址、多节点竞争或身份认证。双方从相同序号状态启动；状态暂存内存，未实现节点单独重启后的会话重建、持久序号或无限重试。真实水声部署还需要按传播距离加入双程时延、收发切换与处理预算，当前 2 s 不是任意距离可用的参数。

## 验证范围

字节层检查标准 CRC 向量、UTF-8、空/最大长度、全部逐位单比特损坏、头部格式与长度错误。波形层检查未知到达延时、不同初相、正负整体多普勒、AWGN、64 字节帧、CRC 损坏、超限长度、截断和噪声。节点层检查序号、重复交付抑制、ACK 匹配与回绕。

演示固定运行正常收发、首次 DATA 丢失、首次 ACK 丢失、全部 DATA 丢失、全部 ACK 丢失五种情况。丢包动作仅存在于测试调度器，节点不会直接读到“成功/失败真值”反馈。全部 ACK 丢失场景应显示 A `exhausted`，同时 B 仅交付一次。

这些确定性软件检查证明当前实现的协议路径可以运行；它们不测量实海误码率、功耗、硬件实时性或长期失步率。历史 V1–V3 的 goodput 数字仍采用原离线真值模型，没有被这次 CRC/ARQ 演示追溯性替换。
